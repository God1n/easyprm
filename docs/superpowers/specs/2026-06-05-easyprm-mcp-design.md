# easyprm — Project Management MCP Server

**Status:** Design approved (pending spec review)
**Date:** 2026-06-05
**Author:** pasindu@terminusapp.ai

## Problem

Solo developers building with AI support struggle with two linked problems:

1. **Planning end-to-end is hard** — getting from a vague idea to a concrete, well-scoped, ordered plan.
2. **Following the plan is hard** — mid-development the thread is lost: scope creeps, the next step is forgotten, and the plan goes stale and stops reflecting reality.

There is no lightweight system that lives *next to the code*, is readable and writable by **both** the human and the AI, survives across sessions, and actively keeps the plan in sync with reality.

## Solution Overview

`easyprm` is a **file-based project management MCP server** (TypeScript / Node, distributed via `npx`). It owns a structured doc tree under `.claude/easyprm/` and exposes MCP tools to create, track, and follow a project from vision down to individual tasks.

### Guiding insight

The value is **not** ticket storage (Linear/Jira do that better). It is that the plan lives next to the code, in git, readable/writable by both human and AI, surviving across sessions. **The enemy is staleness.** Every design decision serves keeping the plan in sync with reality.

### Core principles

- **Authored vs. derived.** Tickets and project docs are authored (by human or AI). Overviews (kanban, DAG, architecture, status) are **machine-generated and never hand-edited**. This is what keeps overviews from going stale.
- **Frontmatter is the contract.** The server only parses machine-readable frontmatter and checklist boxes — never prose. Prose is freeform for humans + AI.
- **Self-guiding tools (Approach 2).** Every tool response carries a `next_steps` hint that pushes the user/AI through the planning → following loop. The workflow lives in the server, so it works in any MCP client (Claude Code, Cursor, etc.) with no companion skill required.
- **Stable, greppable IDs.** `E1`, `E1-T2` — embedded in file/folder names, usable in commit messages to keep plan ↔ code traceable.
- **Fail loud, never corrupt.** Validate-then-write, atomic writes, structured actionable errors.

## File Structure

```
.claude/easyprm/
├── project.md              # AUTHORED — index: name, status, links to docs
├── docs/                   # AUTHORED — open, user-extensible set
│   ├── big-picture.md      #   vision / problem / goals
│   ├── sfr.md              #   software functional requirements (user-facing)
│   ├── trf.md              #   technical requirements / architecture
│   └── db.md ...           #   any extra docs the user adds
├── decisions/              # AUTHORED — lightweight ADRs (FAST-FOLLOW, not v1)
│   └── 0001-<slug>.md
├── epics/
│   ├── E1-<slug>/
│   │   ├── epic.md         # AUTHORED — epic frontmatter + description
│   │   └── tasks/
│   │       ├── E1-T1-<slug>.md   # AUTHORED — full ticket
│   │       └── E1-T2-<slug>.md
│   └── E2-<slug>/ ...
└── overview/               # DERIVED — regenerated on every mutation, do not edit
    ├── kanban.md           #   board grouped by status (Markdown table)
    ├── dependencies.md     #   task DAG (Mermaid)
    ├── architecture.md     #   component map from trf + epics (Mermaid)
    └── status.md           #   "where was I": active epic, in-progress, next step
```

- The planning hierarchy flows: **big-picture → sfr → trf → epics → tasks**.
- `docs/` is an **open set**: defaults are seeded on init, users add their own via `write_doc`.
- Each `overview/` file opens with `<!-- AUTO-GENERATED by easyprm — do not edit -->`.

## Ticket Schema

### Task ticket

One markdown file per task: machine-readable frontmatter + prose sections.

```markdown
---
id: E1-T2
title: Add JWT refresh-token rotation
epic: E1
status: todo            # backlog | todo | in_progress | blocked | in_review | done
depends_on: [E1-T1]     # drives the DAG + get_next_task
tags: [auth, security]
created: 2026-06-05
updated: 2026-06-05
---

# E1-T2 · Add JWT refresh-token rotation

## User Story
As a logged-in user, I want my session to refresh seamlessly so I'm not logged out mid-work.

## Description
<the what & why, free-form context>

## What To Do          # the plan — checklist the AI works through
- [ ] Issue refresh token on login
- [ ] Rotate on use, invalidate prior

## What Is Done         # running log of completed work, filled as you go
- (empty until work starts)

## How To Test          # Definition of Done — must be satisfied to mark `done`
- [ ] Unit: rotation invalidates old token
- [ ] Manual: refresh survives page reload

## Technical Summary    # decisions, files touched, gotchas — the "why" that survives sessions
<filled during/after implementation>

## Comments             # chronological human <-> AI log
- 2026-06-05 (AI): blocked on E1-T1 token store
```

**Schema decisions:**
- **`status`** is the single field powering kanban + status.md. Six states; `blocked` is explicit so DAG/next-task logic can route around it.
- **`How To Test` is the Definition of Done** — the server refuses `→ done` while its boxes are unchecked.
- The server parses **frontmatter** + the checkboxes in `What To Do` / `How To Test` (for progress %). Never the prose.

### Epic ticket (`epic.md`)

Lighter version of the same shape:
- Frontmatter: `id`, `title`, `status`, `goal`, `created`, `updated`.
- Prose: Description, Success Criteria.
- No `depends_on` at the epic level in v1 (keep it simple).

## MCP Tool Surface (v1, ~14 tools)

Each tool returns its result **plus a `next_steps` hint**. Mutating tools **auto-regenerate `overview/`** as a side effect.

**Setup & orientation**
- `init_project` — scaffolds the tree, seeds big-picture/sfr/trf templates.
- `get_status` — returns `status.md`: active epic, in-progress task, blocked items, recommended next step. *"Where was I" — call at session start.*

**Project docs (open set)**
- `list_docs` / `read_doc` / `write_doc` — `write_doc` creates or updates any doc; creating one updates `project.md`'s index.

**Epics**
- `create_epic` — assigns next `E#` ID.
- `update_epic` / `list_epics`

**Tasks (core)**
- `create_task` — assigns `E#-T#`, takes frontmatter + prose.
- `get_task` / `list_tasks` (filter by epic, status, tag)
- `update_task` — set status, edit sections, check/uncheck boxes. **Guards `→ done`** until all `How To Test` boxes are checked.
- `get_next_task` — DAG-aware: returns the highest-priority unblocked task and *why* it's next. *"Don't lose the thread."*
- `add_comment` — appends a timestamped entry to a ticket's Comments log.

**Overviews**
- `regenerate_overview` — manual rebuild (normally automatic), to resync after direct file edits.

**Deferred (not v1):** `add_decision` (ADRs, fast-follow), `detect_drift` (plan-vs-code divergence, stretch).

## Diagram & Overview Generation

All derived from frontmatter — **deterministic, no LLM calls** — so it is fast and reproducible.

- **`kanban.md`** — Markdown table grouped by status (Backlog / Todo / In Progress / Blocked / In Review / Done), each cell links to the ticket file, plus a per-epic progress-% summary line. (Tables read better than Mermaid for boards.)
- **`dependencies.md`** — Mermaid `graph LR` DAG: nodes = tasks (colored by status), edges = `depends_on`. The centerpiece "what unblocks what" view.
- **`architecture.md`** — Mermaid `graph` built from a fenced `easyprm:components` block in `trf.md` (a simple declared list of components + relations) cross-referenced with which epics touch them. Deterministic — does not guess from prose.
- **`status.md`** — "where was I" snapshot: active epic, in-progress task(s), blocked items, and the `get_next_task` recommendation.

Each file opens with the `<!-- AUTO-GENERATED -->` banner.

## Error Handling

**Unified error response** — every tool returns the same shape on failure:

```json
{
  "ok": false,
  "error": {
    "code": "DOD_NOT_MET",
    "message": "Cannot move E1-T2 to 'done': 2 of 3 'How To Test' items unchecked.",
    "field": "status",
    "details": { "unchecked": ["Unit: rotation invalidates old token", "Manual: refresh survives reload"] },
    "recoverable": true,
    "next_steps": "Check the remaining boxes via update_task, or keep status as 'in_review'."
  }
}
```

**Error code catalog (v1):**
- `NOT_INITIALIZED` — `.claude/easyprm/` missing; hint to run `init_project`.
- `VALIDATION_ERROR` — frontmatter/schema violation; `field` + `details` name the problem.
- `NOT_FOUND` — referenced epic/task/doc ID doesn't exist.
- `DEPENDENCY_INVALID` — `depends_on` references a missing task.
- `DEPENDENCY_CYCLE` — adding this edge would create a cycle; `details` lists the path.
- `DOD_NOT_MET` — `→ done` blocked by unchecked `How To Test` items.
- `ID_CONFLICT` — internal guard; server-assigned IDs never collide.
- `FILE_CONFLICT` — file changed on disk unexpectedly / unparseable frontmatter on read; hint to fix or `regenerate_overview`.

**Principles:**
- **Fail loud, never write a corrupt file** — validate-then-write, atomic writes.
- Every error is **actionable** via `next_steps`.
- `recoverable` tells the client whether retrying differently could work.
- **Hand-edit tolerance:** the server re-parses from disk on each call (no in-memory cache to drift); unparseable files surface `FILE_CONFLICT` rather than crashing.

## Other Behaviors

- **ID integrity:** IDs are server-assigned and never reused.
- **Idempotent regeneration:** overview rebuild is a pure function of the ticket set — identical output for identical input, safe to run anytime.
- **Cycle detection:** `get_next_task` and DAG generation detect dependency cycles and surface them rather than looping.

## Testing Strategy

- **Unit tests** on the pure core: frontmatter parse/serialize, DAG resolution, next-task selection, diagram rendering against fixtures.
- **Integration tests** driving the MCP tools against a temp `.claude/easyprm/` tree, asserting on-disk file contents.

## Scope Boundaries

**In v1 (the spine):**
- Authored/derived file model + init.
- Full ticket + epic schema with frontmatter contract.
- ~14 tools covering create → track → follow.
- Dependency DAG + `get_next_task`.
- Session continuity (`get_status` / `status.md`).
- DoD enforcement on `→ done`.
- Deterministic diagram/overview generation.
- Unified error handling.

**Fast-follow:** ADRs (`add_decision`, `decisions/`).

**Stretch:** drift detection (`detect_drift`) comparing plan vs. git history / codebase; an optional Claude Code companion skill for a richer guided planning conversation.
